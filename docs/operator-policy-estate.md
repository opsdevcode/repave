# Policy repos and the operator

How **Policy** family golden paths (`checkov-policy`, `opa-policy`, `azure-policy`)
fit the repave operator and estate upgrades.

## What gets generated

Each policy blueprint publishes a standalone repository with `repave.yaml`
(`GoldenPathArtifact`) describing artifact type and governance pins. Gates run at
generate time and in the repo's CI (`repave gates`).

| Artifact type | Blueprint | Primary gate |
| --- | --- | --- |
| `checkov-policy` | `checkov-policy-generic` | `checkov` |
| `opa-policy` | `opa-policy-generic` | `opa` (Conftest) |
| `azure-policy` | `azure-policy-generic` | `azure-policy` (definition JSON) |

Portal walkthrough: [policy-golden-paths-demo.md](policy-golden-paths-demo.md).

## Inventory today (GA)

The operator reads **observed** pins from `repave.yaml` on `spec.localPath` — the
same contract as Terraform modules. Policy repos generated by repave include
`spec.checkovPolicy`, `spec.opaPolicy`, or `spec.azurePolicy` plus shared
`spec.governance` baseline metadata.

**Example:** register a policy repo beside a module fixture:

```yaml
apiVersion: repave.dev/v1alpha1
kind: GoldenPathRepo
metadata:
  name: opa-policy-platform-estate
spec:
  localPath: /path/to/opa-policy-platform-estate
  blueprintRef:
    name: opa-policy-generic
    version: "0.3.0"   # desired catalog pin
```

When catalog blueprint or standard versions move ahead of the repo's provenance,
status shows **OutOfDate** and `repave plan-upgrade` JSON appears on status — same
remediation flow as [terraform-minimal](../operator/testdata/modules/terraform-minimal/).

## Not in GA scope

- Cloning **remote** policy repos via `spec.repoURL` for observed pins (ADR 001).
- Policy-specific CRD fields beyond generic blueprint/standard drift.
- Pushing Azure Policy **assignments** or initiatives — definitions-only golden path.
